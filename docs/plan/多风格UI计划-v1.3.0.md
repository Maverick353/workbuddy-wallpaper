# workbuddy-wallpaper · 多风格可切换 UI 计划（v1.3.0）

> 由 grilling 会话产出：**3 轮盘问**（14 项决策全部由用户拍板）+ **2 个只读勘察子代理**（样式架构 / 风格与许可证调研）。
> **状态：待确认后执行。执行起点 = v1.2.1（更新机制优化）完成并通过验收之后。**
>
> 一句话目标：把现在**唯一一种**界面风格（玻璃拟态）拆成「**形态 × 配色**」两个可独立切换的维度，
> 并把「标准风格」定义为**与今天逐像素一致**的那一组。

---

## 〇、结论摘要与已定决策

**这次不是"再画一套皮肤"，而是把样式从"散落的硬编码"改造成"可切换的契约"。**
项目已有一层部分 token（`panel.js:138-141` 的 11 个 `--wdw-*`）和一个**尚未接线的换肤能力**
（`window.__wdwRopeBuddy.setStyle('theme'|'black'|'white'|'glass')`），但**光照、阴影、边框、玻璃底大面积硬编码**，
且有 **5 个各自独立的 `<style>`**、**没有统一主题入口**。所以工作量的大头在"抽取与分层"，不在"配色"。

### 已定决策（14 项）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 「风格」的口径 | **整套风格** = 注入 UI 外观 + 宿主透明化强度 + 文字色 + 字体（壁纸不动） |
| 2 | 切换维度 | **形态 × 配色 独立可混搭** |
| 3 | 规模 | **形态 5 × 配色 6 = 30 组合** |
| 4 | 与 v1.2.1 的关系 | **排在 v1.2.1 之后**（两者都要改 `panel.js`/`theme-css.js`/`index.js`） |
| 5 | 形态清单 | **标准（玻璃）/ 扁平 / 新拟物 / 终端 / 纸墨** |
| 6 | 配色清单 | **跟随宿主（标准）/ 极地蓝 / 深紫夜 / 暖褐 / 护眼绿 / 日光米（浅色）** |
| 7 | 持久化 | **服务端 `<数据目录>/appearance.json` + `GET/POST /api/appearance`** |
| 8 | 验收 | **全矩阵自动验**：30 组合逐一切换 + 截图 + **自动计算 WCAG 对比度** |
| 9 | 不兼容组合 | **允许 + 当场提示对比度**（不禁止） |
| 10 | 预设内容 | 风格**自带推荐值并切换时应用**；用户手改过的项**按风格分别记住** |
| 11 | 吉祥物 | **统一进新体系**（材质跟形态、颜色跟配色；缩放/隐藏保留） |
| 12 | 切换入口 | **新增第 6 个页签「外观」**；背景透明度补到「系统」页 |
| 13 | 命名与许可 | 界面**只用中性中文名**；来源与许可证写进 `THIRD-PARTY-NOTICES.md` |
| 14 | 明令不做 | 自定义主题导入导出、跟随系统深浅自动切、风格绑壁纸、拆 `panel.js` |

### 本计划采纳的外部做法（来自技能《主题换肤方案》）

已安装并按它的方法论校订本计划：**采纳 4 条、说明差异 2 条**。

| 采纳 | 落在哪 / 改了什么 |
|---|---|
| **设计令牌三层结构**（原始档位 → 语义变量 → 组件引用；组件只认第二层） | §2.2 —— **原计划是两层，已改** |
| **语义变量名不得含颜色或材质词** | §2.2 —— 并**修正现有命名**：`--wdw-glass-line/fill/fill-hi` → `--wdw-line` / `--wdw-fill` / `--wdw-fill-hi` |
| **最小变量清单** | §2.2 —— 它给 20 项，我们按本项目需要扩到 32 项，**补上了最容易漏的 `on-accent` / `focus-ring` / `overlay` / `disabled` / `ok-warn-info`**（原计划只有 `danger`） |
| **换肤自检 12 条 + 一行硬编码扫描命令** | §4.3 第 6 条、§七验收清单 |

| 说明差异 | 为什么 |
|---|---|

| 「首屏恢复必须写在 `<head>` 里防 FOUC」 | 场景不同：我们的外观**随 payload 一起注入**，UI 首帧就是对的；要防的是另一件事（§4.3 第 7 条） |

> 它的红线「不照抄他人产品皮肤」与我们的做法一致：我们取的是开源色板的**颜色数值**，形态是自研，不模仿任何具体产品。

## 二、风格切换机制设计

### 2.1 数据与渲染分层

```
core/skins.js            ← 纯数据 + 纯函数（零依赖、可在 Node 里单测）
  ├─ FORMS     形态 5 种：形态决定"形状与材质"（圆角/阴影/描边/模糊/装饰/字体角色）
  ├─ PALETTES  配色 6 套：配色决定"颜色"（表面/文字/强调/线条/阴影色）
  ├─ resolve(formId, paletteId) → 合并后的 token 表 + 实测对比度 + 警告列表
  └─ contrast() / wcagRatio()   ← 纯计算，因此"可读性"能被自动化断言
        ↓ 服务端读取
ui/dsh-ui/index.js  dshUIExpression(opts)   ← 唯一的 payload 组装点（已存在）
        ↓ 随 payload 注入
ui/dsh-ui/skin.js   运行时应用：写 <style id="wdw-skin-style"> + 根属性
        ↓
面板「外观」页 / 系统页  →  POST /api/appearance  →  <数据目录>/appearance.json
```

**为什么把数据放服务端**：面板的 payload 本来就是服务端拼的（`ui/dsh-ui/index.js:266` 的 `dshUIExpression(opts)`，
由 `scripts/start-ui.js:216` 与 daemon 的注入钩子调用）。服务端读一份 `appearance.json` 放进 payload，
**注入时零延迟、多窗口天然一致、重装与更新都不丢**。

### 2.2 token 契约（改造的核心）：三层结构

现有 token 只有 11 个（`panel.js:138-141`），且只挂在面板根上、**混着材质词命名**（`--wdw-glass-line/fill`）。
新契约改成**三层**，并把第二层**全部挂到根作用域选择器上**（`:root[data-wdw-form=…][data-wdw-palette=…]`）：

```
第一层  原始档位（PALETTE 提供）   --p-surf-1: #2e3440;     只描述"第几档明暗"
   ↓
第二层  语义变量（FORM × PALETTE） --wdw-surface: var(--p-surf-1);   描述"干什么用"
   ↓
第三层  组件引用                   .p-btn{background:var(--wdw-surface)}   组件只认第二层
```

**铁律（两条）**：
- **组件里不出现任何 `#`/`rgb()` 字面量** —— 出现即换肤失败（详见 §4.3 的自动化扫描）。
- **第二层的名字里不得含颜色或材质词**（`--wdw-ink` ✅ / `--wdw-glass-fill` ❌）。
  ⚠️ **这条是对现有一处命名的修正**：`--wdw-glass-line` / `--wdw-glass-fill` / `--wdw-glass-fill-hi`
  是**按材质命名**的，扁平/纸墨形态下它们与"玻璃"毫无关系 → 在批次 0 一并改名为
  `--wdw-line` / `--wdw-fill` / `--wdw-fill-hi`。

**第一层：原始档位（每套配色提供约 21 个，"按明暗分档、不含用途"）**

| 组 | 档位 | 为什么需要 |
|---|---|---|
| 表面阶梯 | `--p-surf-0…3`（4 档） | 形态要"同色系上下偏移一档"：新拟物的双向阴影、扁平的 hover、纸墨的纸面 vs 卡片 |
| 文字阶梯 | `--p-ink-0…3`（4 档） | 主/次/弱/禁用 |
| 线 | `--p-line` | 描边与分隔线 |
| 阴影 | `--p-shade` / `--p-shine`（2 档） | **一暗一亮**：新拟物靠这两个"挤出/凹陷"；扁平把它们设透明 |
| 强调 | `--p-accent` / `--p-accent-hover` / `--p-accent-soft` / `--p-on-accent`（4 档） | 悬停、软底（选中行/标签底）、**强调之上的文字**（最易漏：深色下常要改成深字） |
| 语义 | `--p-ok` / `--p-warn` / `--p-danger` / `--p-on-danger`（4 档） | 成功/警告/危险 + 危险之上的文字 |
| 遮罩 | `--p-overlay` | 弹窗背后 |

**第二层：语义变量（约 32 项 = 通用 20 项 + 本项目专有 12 项）**

| 分组 | 变量 | 备注 |
|---|---|---|
| 背景层 | `--wdw-surface` / `--wdw-surface-2` / `--wdw-surface-3` | 面板底 / 次级区块 / 悬浮与输入底（对应 `--p-surf-0…2`） |
| 线 | `--wdw-line` / `--wdw-line-strong` / `--wdw-border-w` | 边框 / 强调边框 / **描边宽度**（玻璃半透明、扁平 1px 实线、纸墨 1px 细线） |
| 阴影 | `--wdw-shadow` / `--wdw-shadow-hi` | 外阴影 / 高光与内阴影（新拟物全靠这两个） |
| 文字 | `--wdw-ink` / `--wdw-ink-2` / `--wdw-ink-3` / `--wdw-ink-disabled` / `--wdw-ink-inverse` | 现有 3 项 + 禁用 + 反色 |
| 强调 | `--wdw-accent` / `--wdw-accent-hover` / `--wdw-accent-soft` / `--wdw-on-accent` | 现有 1 项 → 补齐**悬停/软底/其上文字** |
| 语义 | `--wdw-ok` / `--wdw-warn` / `--wdw-danger` / `--wdw-on-danger` / `--wdw-info` | 现有只有 `--wdw-danger`（红点/错误态用它） |
| 状态 | `--wdw-disabled-bg` / `--wdw-focus-ring` / `--wdw-overlay` | **焦点环是无障碍必需**（现有完全没有） |
| 形状 | `--wdw-radius` / `--wdw-radius-sm` / `--wdw-ui-h` / `--wdw-blur` | 圆角 / 小圆角 / 控件高 / **模糊半径（扁平与纸墨设 0）** |
| 动效 | `--wdw-ease` / `--wdw-dur-fast` / `--wdw-dur` | 补一档时长，消除 `panel.js:246-256` 的硬编码 |
| 排版 | `--wdw-font` / `--wdw-font-mono` / `--wdw-font-display` / `--wdw-tracking` | UI 字体栈 / 等宽 / 标题字体 / 字距 |
| 装饰 | `--wdw-decor` | 形态专属底纹（终端 = 扫描线；其余 `none`） |

**"切换形态"本质上是切换这 32 项的取值**：扁平/纸墨把 `--wdw-blur` 设 0、`--wdw-shadow` 设透明；
新拟物把 `--wdw-line` 设近乎透明、让 `--wdw-shadow` / `--wdw-shadow-hi` 承担全部层次；
玻璃保持现状值。**这正是它能被自动验收的原因。**

> 第一层为什么要独立存在：形态要能"**只挪一档**"而不改配色（新拟物的暗面 = `--p-surf-1`，亮面 = `--p-shade` 的补色），
> 配色要能换而不碰形态。两层分开，30 个组合才不会变成 30 份手写样式。


### 2.3 运行时切换：不重注入

照抄项目里**已验证的成熟范式**（`ui/dsh-ui/index.js:254` 的 `window.__wdwFont.set()` 直接重写
`<style id="wdw-font-style">` 的 textContent，不重新注入）：

```
window.__wdwAppearance = {
  get()  → 当前 {form, palette, warnings, contrast}
  set(form, palette) → ① 改 documentElement 的 data-wdw-form / data-wdw-palette
                       ② 重写 <style id="wdw-skin-style"> 内容
                       ③ POST /api/appearance（持久化）
                       ④ 通知吉祥物：__wdwRopeBuddy.setStyleFromAppearance(...)
}
```

**宿主透明化强度（蒙版）** 属于另一条链路：它由服务端生成 CSS（`core/theme-css.js`），
走**已有的 `/api/mask` 成熟链路**触发重新注入。切风格时若风格带推荐蒙版值，按决策 10 处理
（应用推荐值，但用户手改过的值**按风格分别记住**，切回来恢复用户自己的值）。

### 2.4 持久化

`<数据目录>/appearance.json`：

```json
{
  "form": "standard",
  "palette": "host",
  "perForm": {
    "flat":   { "mask": 0,   "buddyStyle": "glass", "overridden": ["mask"] },
    "terminal": { "mask": 40, "buddyStyle": "black" }
  }
}
```

- `perForm[formId].overridden` 记录"用户手改过哪些项"——这就是决策 10 的落法。
- `GET /api/appearance` 返回当前值 + 由 `core/skins.js` 算出的对比度与警告。
- 新路由要**加入 `ROUTES` 白名单**（`server/routes.js:29-43`）与 `isApiPath`（同文件 `:60-62`），否则 daemon 转发不到。

### 2.5 吉祥物纳入体系

它已经有 `setStyle('theme'|'black'|'white'|'glass')` / `setScale` / `setHidden`（`ui/dsh-ui/rope-buddy.js:102-105,254-256`），
只是面板没接线。改造：

- **材质/姿态** 由「形态」决定（玻璃→`glass`、终端→`black`、纸墨→`white`、扁平/新拟物→跟随配色明暗）
- **颜色** 由「配色」决定
- 缩放与隐藏**保留为独立设置**（它们与风格无关，硬绑反而别扭）

### 2.6 兼容性：算出来，不是定规则

决策 9 要求"允许 + 提示"，所以**不做硬编码的兼容表**，而是：每个形态提供**明/暗两套配方**
（`recipeLight` / `recipeDark`），由配色的 `light` 标志选择；再用 `contrast()` 对最终 token 表**实测**，
低于门槛的组合返回警告，面板上显示实测数值。

这样 **30 个组合全部可用**，警告只出现在"确实算出来不够"的地方——而不是"我规定新拟物必须配浅色"。
（新拟物在深色下是成立的已知变体，只是暗面高光要重做。）

**深色配方必须遵守的四条**（不是"反色"，是重做一次配色）：

| 要改的 | 浅色 | 深色 |
|---|---|---|
| 表面底 | 浅灰，不用纯白刺眼 | **不用纯黑**（纯黑 + 玻璃会显脏） |
| 层级的表达方式 | 越靠上越白 + 阴影 | **越靠上越亮**——深色下阴影基本看不见，光靠阴影会"糊成一片" |
| 强调色 | 原值 | **降饱和 + 提亮** |
| 强调之上的文字 | 白字 | **常要改成深字**（亮底按钮配深字） |

⇒ 直接后果：**新拟物在深色下必须改用"亮面向上抬"而不是"阴影向下压"**；
**扁平与纸墨也会失去它们赖以区分的阴影**，所以每个形态的暗色配方都要单独调，不能靠变量替换自动得到。

## 三、风格清单：来源与差异

### 3.1 五种形态（我们自己写 CSS，不引入任何框架）

| id | 名称 | 关键 CSS 手法（≤2 行） | 可用性风险 | 视觉反差 |
|---|---|---|---|---|
| `standard` | **标准（玻璃）** | 现状：`backdrop-filter` 模糊 + 半透明白描边 + 极淡白填充 + 柔和外阴影 | **深色/花壁纸上可读性依赖蒙版** | 基准 |
| `flat` | **扁平** | `--wdw-blur:0`、阴影透明、纯色块 + 1px 实描边、强调色填充按钮、圆角略小 | 层次感弱；花壁纸上"压不住" | 中（降噪向） |
| `neumorph` | **新拟物** | 面板与底同色系；**双向柔和阴影**（一亮一暗）+ 极细双向描边；无边框线、无模糊 | **低对比、边界不清**（必须靠实测对比度把关） | 高 |
| `terminal` | **终端复古** | 硬直角、纯色深底、荧光前景、`repeating-linear-gradient` 做扫描线（`--wdw-decor`）、无模糊无阴影 | **等宽字体承载中文长文可读性差** → 等宽只作用于标号/数值/标题，正文保持系统字体 | 高 |
| `paper` | **纸墨** | 米白/暖灰底、深墨字、高留白、1px 低对比细分隔线、无阴影无模糊、方角或极小圆角 | **浅底在深色壁纸上需要蒙版配合**（风格带推荐蒙版值） | 高 |

> 备选（本次不纳入，已评估）：霓虹赛博（长时间刺眼、与终端同属暗底发光系）、亚克力 Fluent（与玻璃同源、差异小）、
> 粗野/新粗野（高饱和硬阴影，作为可选风格噪音过大）。

### 3.2 六套配色（色值取自知名开源色板，界面用中性中文名）

| id | 界面名 | 来源色板 | 许可证 | 明暗 | 取哪些角色 |
|---|---|---|---|---|---|
| `host` | **跟随宿主** | 现状（映射宿主 `--wb-*`） | ——（我们自己的映射） | 跟随宿主 | 保持今天的行为不变 |
| `polar` | **极地蓝** | Nord | **MIT** | 深 | `nord0/nord1` 作表面、`nord4/nord3` 作文本、`nord8` 作强调 |

## 四、如何不影响现有功能

### 4.1 五条不可破坏的契约（写进代码注释与断言）

| # | 契约 | 为什么 |
|---|---|---|
| **C1** | 生成的背景 CSS 必须含 `#root:not(#wdw-noop){background:`，且**不得**出现裸 `#root{background` | 已被 `scripts/verify.js:228-232` 钉死；特异性一降，宿主规则立刻盖掉壁纸 |
| **C2** | `CHROME_CSS` 必须含 `#root:not(#wdw-noop){background-image:none` | 同上（同机还有第二套注入在抢 `#root`） |
| **C3** | 所有新常量**必须走 `payload`**，不得引用模块级常量 | 面板/吉祥物/背景层是 `toString()` 注入的，注入侧取不到模块作用域 |
| **C4** | **纯样式变化不 bump `WIRE_VER`**；只有动 DOM 结构才 bump | 重注入协议按指纹判定，误 bump 会触发不必要的重建 |
| **C5** | 换肤过程**不得移除 `#wdw-rope-buddy` 节点** | `scripts/start-ui.js` 每 **15 秒**轮询该节点，缺失就判定"未注入"并**整段重新注入** |

### 4.2 改造清单：把硬编码逐处换成 token

| 文件:行号 | 现状 | 改法 |
|---|---|---|
| `ui/dsh-ui/panel.js:138-141` | 11 个 token 定义 | 扩到约 24 个；改挂根作用域 |
| `ui/dsh-ui/panel.js:142-244` | 玻璃底 + 模糊、悬浮岛阴影、段控底、卡片底 `#0b0d12`、边框 `rgba(255,255,255,.14)` | 全部换 token（`--wdw-surface*` / `--wdw-line` / `--wdw-shadow` / `--wdw-blur`） |
| `ui/dsh-ui/panel.js:246-256` | 动效常量硬编码 `220ms/260ms/180ms/160ms/140ms`（与 `--wdw-dur-*` 重复） | 收敛到 `--wdw-dur` / `--wdw-dur-fast` |

### 4.3 回归防线（"不影响现有功能"靠这个证明，不靠感觉）

1. **纯重构批次不许改观感**：批次 0（token 抽取）结束时，切到 `standard/host` 的截图必须与改造前**逐像素一致**。
2. **现有 89 条断言零放宽**：只允许新增，不允许为了通过而修改已有断言的期望值。
3. **重注入后状态恢复**：等 15 秒让轮询触发一次重注入，确认风格与蒙版仍在（这是 payload 带 appearance 的验证）。
4. **多窗口一致**：两个窗口同时打开，一边切换，另一边刷新后应一致（服务端为源）。
5. **更新/回滚不影响外观**：`appearance.json` 在数据目录，不在代码目录 → 更新与回滚都不该动它。
6. **硬编码扫描（自动化，每次改完都跑）**：`ui/` 与 `core/theme-css.js` 里**零命中** `#xxx` / `rgb()` / `rgba()`
   （**唯一例外是色板数据文件 `core/skins.js` 与 vendored 的 `renderer/`**）：

   ```bash
   grep -rnE "#[0-9a-fA-F]{3,8}\b|rgba?\(" ui/ core/theme-css.js | grep -v "var(--"
   ```

   这条是"组件里绝不写死颜色"的机器化，也是这套东西**能不能长期维护的分水岭**——
   漏一处，加第 7 套配色时就会冒出一块"浅色主题下的白卡片"。
7. **不能先渲染成标准色再跳变**：appearance 随 payload 到达，我们的 UI 首帧就该是目标风格。
   要验的是"注入到达那一瞬"不会先画一版标准色（用连拍截图或注入计数证明）。
